# Migration Room 5 → 6 — les pleins et recharges complets

**Préversion Android 0.4.0-beta.12, pas une version stable.** Cette évolution concerne le stockage local, pas le format d’échange : import JSON v1 à v3 et export v3 restent distincts des versions Room. **Avant toute mise à jour, effectuer une sauvegarde externe et vérifier le fichier**, sur chaque appareil concerné. Le JSON est non chiffré ; conserver au moins une copie sûre hors du téléphone. Tester d’abord avec des données fictives sur un appareil ou émulateur distinct, sans toucher à une base unique.

## Périmètre

- Depuis beta.11 / Room 5, migration **5 → 6** à l’ouverture ; depuis Room 4, chaîne 4 → 5 → 6 ; depuis Room 3, 3 → 4 → 5 → 6 ; depuis Room 2, 2 → 3 → 4 → 5 → 6. La chaîne 1 → 2 → 3 → 4 → 5 → 6 est enregistrée. Ce ne sont pas les versions du JSON.
- Après les véhicules et interventions, les **pleins et recharges / fills** ont leur source complète : `complete_fills` stocke l’identifiant, le véhicule et les 11 champs connus `date`, `odometer`, `volume`, `unit`, `unitPrice`, `total`, `full`, `station`, `notes`, `createdAt`, `updatedAt`. Présence, nullité et valeurs externes sont distinguées ; les nombres sont stockés en textes de jetons JSON exacts, non en `Double` pour reconstruire les données. `full` est un booléen stocké en entier SQLite ; une valeur autre que 0 ou 1 bloque la reconstruction. La représentation sait distinguer absence et `null`, mais la validation d’un plein accepté exige que `full` soit un booléen.
- `complete_fill_values` et `complete_fill_value_chunks` conservent les valeurs individuelles longues et les **seules propriétés inconnues**, avec découpage et SHA-256. Une extension peut contenir des objets, listes ou médias futurs, mais n’est pas une copie JSON complète du plein. `compat_records` conserve résumés, métadonnées et empreinte ; `fills` reste une projection de requête. L’export ne prend pas cette projection comme solution de repli. La relation vers le véhicule est différée pour accepter les collections importées dans n’importe quel ordre à l’intérieur de la transaction.
- **Huit autres collections** — trajets, dépenses, rappels, symptômes, modèles CQ, contrôles, documents et réglages — gardent leurs JSON complets dans `compat_chunks`. La source typée unique pour les onze collections n’est donc pas achevée. La suppression immédiate avec Undo transactionnel n’est pas réalisée ; le bandeau actuel reste une suppression différée.

## Protection des données

Room encadre la migration d’une transaction. Pour chaque plein, l’ancien contenu est relu en vérifiant ses blocs, leur ordre, leur taille, leur empreinte et l’UTF-8. L’identité et le véhicule sont vérifiés ; le code encode les nouveaux champs, relit les données réellement écrites dans SQLite et compare l’objet reconstruit à l’original. Les relations sont vérifiées avant de supprimer, en fin de transaction seulement, les anciens blocs JSON complets **des pleins**. En cas de corruption, incohérence, valeur illisible ou échec, l’opération doit échouer et la transaction doit être annulée ; cela ne remplace pas une sauvegarde externe.

Les propriétés dupliquées, y compris imbriquées, sont refusées dans un plein plutôt que supprimées silencieusement. Certains nombres exceptionnellement longs ne sont pas lisibles fidèlement par le lecteur strict : l’opération est alors refusée. Le nouveau contrôle s’applique aux imports et aux données encore lisibles dans l’ancienne base ; il ne peut pas restituer une donnée déjà altérée par une ancienne version. Les chaînes longues, y compris les unités Unicode isolées, sont conservées dans des blocs adaptés. Aucune valeur de temps ou de mémoire n’est garantie.

L’export vérifie la source complète et son empreinte ; en cas de donnée absente ou altérée, il est interrompu au lieu de reconstituer un plein depuis l’index tronqué. Les créations, modifications et suppressions d’un plein mettent à jour ses métadonnées et sa projection dans la même transaction que la source complète, et le compteur du véhicule si nécessaire. À l’édition, les champs inchangés préservent leur présence, leur nullité et leur texte numérique, tandis que les champs réellement modifiés restent validés. Les limites de taille des formulaires s’appliquent toujours : certaines valeurs importées trop longues peuvent empêcher l’enregistrement sans être tronquées.

## Résultats de cette préversion

108 tests JVM ciblés et 270 tests JVM au total ont réussi, sans échec ni ignoré avec les fichiers fictifs. Lint : 0 erreur/17 avertissements. Les APK debug et de test ont été compilés ; 17 tests instrumentés sont compilés mais **aucun n’a été exécuté** faute d’appareil/émulateur. Depuis la livraison, un rapport Windows indique 266 tests réussis et 4 ignorés sur 270 ; il contient les tests beta.12. L’utilisateur indique 25 min 26 s pour le lancement correspondant à ce rapport. Le dossier Windows actuel indique beta.12, code 16. Les tests instrumentés sur appareil ne sont pas attestés. Aucun benchmark physique.

## Retour arrière et validations

Une ancienne application Room 5 ou antérieure ne sait pas ouvrir directement une base déjà migrée en Room 6. Ne pas désinstaller, vider les données ni forcer une rétrogradation en cas de problème ; conserver la sauvegarde externe d’avant mise à jour et tester une éventuelle restauration séparément.

Les tests JVM simulés et les tests instrumentés sont deux contrôles différents. Les tests instrumentés `MigrationTestHelper` doivent être **exécutés** sur un appareil ou émulateur avant l’utilisation de données réelles. Les tests sur PC ne garantissent pas l’absence de problème sur un téléphone. La PWA 1.5.1 peut arrondir certains nombres JSON très grands ou très précis : une représentation exacte côté Android ne garantit pas la fidélité numérique d’un aller-retour par la PWA ; garder les fichiers originaux.
